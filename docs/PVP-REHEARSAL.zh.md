# 共享攻防演练

这是独立 Godot 客户端的本机四账号演练。账号 1、2 为一组联盟，账号 3、4 为另一组。四份城池进度各自保存，服务器统一处理行军、援军、自动战斗与返程。演练初始兵力、资源和战争状态为服务器预置，不改变原网页的新手礼包或正式战争准备期。

## 启动

开发目录运行 Node 20+：

```sh
node scripts/start-pvp.mjs --data-dir .local/shared-pvp --web-dir build/web
```

保持服务运行，从自动打开的本地邀请页面分别选择账号。邀请页面与凭据仅存于私有演练目录，不能放进 `build/web`。网页加入后立即清除地址里的令牌片段；刷新页面后，请从本地邀请页面再次进入。共享进度保持在服务器上，客户端保存待确认的操作编号，不保存账号令牌。

Windows 桌面包：完整解压，先运行 `StartPvP.cmd`，再分别运行 `PlayPvP1.cmd`～`PlayPvP4.cmd`。Windows 网页包运行 `StartPvP.cmd`；macOS/Linux 网页包运行 `./start-pvp.sh`。单人试玩入口继续使用原来的 `ThreeKingdoms.exe` / `StartWeb.cmd`，与共享演练分开。

开发机桌面客户端也可加入相同服务：

```sh
node scripts/join-pvp.mjs --native --slot 4 --data-dir .local/shared-pvp --godot /absolute/path/to/Godot
```

## 一场完整攻防

1. 用账号 4 打开“共享战争”，向同盟账号 3 派遣 100 名长枪兵。观察行军、抵达驻扎和将领忙碌状态。
2. 用账号 1 向账号 3 派遣骑兵与弓兵。出征即时扣除兵力与粮草，地图显示路线和抵达倒计时。
3. 服务器到时自动处理战斗，守方与实际抵达的援军共同参战。客户端离线不暂停行军，也不需要逐回合点击确认。
4. 双方查看共享战报，核对攻守生还、永久损失、伤兵和缴获。守方统计含盟友援军，不能直接当作本账号的损失。
5. 攻方部队返城后，战报显示实际交付的缴获。返程携带与已入库分开显示；不会把战斗时的缴获预先计入资源。
6. 幸存援军可由所属账号召回，兵力与伤兵始终归原玩家。服务重启会继续处理已抵达的行军，原编号重试不会重复结算。

## 本轮边界

演练服务仅接受本机连接。当前没有跨电脑登录、公网数据库、Steamworks 或百人负载验证。后续正式部署需要真实账号与托管权威数据库；本地令牌和演练数据不承担正式账号功能。

本轮只开放玩家城池攻防。NPC 野地出征仍在私人试玩中，避免把原作私人主城坐标与共享城址混用。主城保底不能占领；渡口通路、联合计划与分阶段攻城将在共享闭环验证后另做。

原网页仓库、原 GitHub Pages、`vendor/legacy` 和私人进度保持现状。原作共享规则新增快照位于 `vendor/shared`，来源与 SHA256 在其 `provenance.json` 中记录。

## 断线与升级

同账号多个窗口按操作编号分别保存待确认记录。重连会使用原编号恢复；旧回执可以确认操作，但不会覆盖较新的库存、部队或世界状态。账号与服务器身份不同的记录互不读取。网页令牌不持久化，刷新后仍须从私有邀请页面重新加入。

升级前关闭旧版客户端：新版能读取旧的单文件回执，但旧客户端仍使用旧写法，不能提供新版的多窗口保证。不要手动删除未确认操作来重试扣兵或交易。

同一演练目录只允许一个服务进程。正常服务崩溃后的旧进程锁可自动恢复；若进程恰好在获取锁期间中断，服务会保留 `.shared-bridge.reclaim.lock` 并拒绝启动。仅在确认所有演练进程均已退出后移除这个恢复保护文件，再重新启动；保留世界文件和凭据。
